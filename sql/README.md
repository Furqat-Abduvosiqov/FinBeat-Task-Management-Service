# Задание 2 - поденные суммы платежей

Табличная функция принимает `ClientId` и интервал дат и возвращает по одной строке на каждый
календарный день интервала (обе границы включаются) с суммой платежей клиента за этот день. Если
платежей в этот день не было, в строке стоит `0`, а не пропуск. Интервал может охватывать несколько
лет.

## Файлы

| Файл | Назначение |
|---|---|
| `sqlserver/ClientDailyPayments.sql` | Буквальное прочтение задания: типы `bigint` / `datetime2(0)` / `money`, инлайн-табличная функция |
| `postgresql/client_daily_payments.sql` | Та же логика на PostgreSQL - эту версию проект умеет запускать, и она покрыта автотестами |

В задании таблица названа `ClientPayments` в DDL и `client.Payments` в примерах. Здесь используется
вариант со схемой: `client.Payments` в SQL Server и `client.payments` в PostgreSQL.

## Соответствие типов

| Задание (T-SQL) | PostgreSQL | Почему так |
|---|---|---|
| `bigint` | `bigint` | Совпадает |
| `datetime2(0)` | `timestamp(0)` | Момент без часового пояса, точность до секунды. Не `timestamptz`: иначе переход на летнее время сдвигал бы границы суток |
| `money` | `numeric(19, 4)` | `money` в SQL Server - это масштабированное целое с четырьмя знаками после запятой; `numeric(19, 4)` даёт ту же точность без потерь. Тип `money` в PostgreSQL зависит от локали, поэтому он не подходит |

## Принятые решения

### Сначала агрегируем платежи, потом присоединяем дни

Порядок действий важнее, чем кажется. Напрашивается соединить список дней с платежами по условию
`платёж внутри суток` и агрегировать результат. Так и было сделано сначала, и это работает, но
условие соединения - диапазонное, а не по равенству. Хеш-соединение для диапазона невозможно,
поэтому база идёт в индекс отдельно за каждым днём: интервал в шесть лет - это 2192 отдельных
спуска по индексу.

Поэтому сейчас сумма считается один раз за весь интервал, а дни присоединяются к готовым суммам по
равенству дат. Один диапазонный поиск по индексу вместо тысяч точечных, дальше обычное соединение
по равенству. Замеры на таблице в 2 млн платежей (300 клиентов, у первого 3277 платежей):

| Интервал | Было | Стало |
|---|---|---|
| 1 месяц | 0,44 мс / 100 буферов | 0,30 мс / 10 буферов |
| 1 год | 1,53 мс / 1106 буферов | 1,02 мс / 14 буферов |
| 6 лет | 9,06 мс / 6603 буфера | 4,05 мс / 30 буферов |

На SQL Server картина та же: было `scan count 2192, logical reads 9432`, стало `scan count 1,
logical reads 34`.

Обратите внимание, что в новом варианте колонка всё-таки приводится к дате - `dt::date` в
`GROUP BY`. Это не противоречит правилу «не приводить колонку к дате»: правило относится к
**отбору**, а не к группировке. В `WHERE` стоит сырая колонка и полуоткрытый интервал
`[начало, конец + 1)`, поэтому индекс отрабатывает как диапазонный поиск; приведение к дате
применяется уже только к отобранным строкам, и мешать ему нечему.

### Дни строятся как `timestamp`, а не `timestamptz`

В PostgreSQL у `generate_series` нет перегрузки для `date`. Если передать в неё даты, выбирается
перегрузка с `timestamptz` (это предпочитаемый тип в своей категории), и дни получаются с часовым
поясом. Дальше `timestamp(0)`-колонка сравнивается с `timestamptz`, то есть результат начинает
зависеть от часового пояса сессии.

Это не теория. Прибавление `INTERVAL '1 day'` к `timestamptz` - это арифметика по местному времени,
и в зонах, которые переводят часы **в полночь** (`America/Santiago`, `Asia/Tehran`,
`America/Asuncion`), после первого же перехода ряд съезжает с `00:00` на `01:00` и там и остаётся.
Последствия два, и оба молчаливые:

- последний день интервала пропадает: на запросе за 2016-2024 возвращается 2770 строк вместо 2771;
- сутки сдвигаются на час, и платёж от `2024-03-10 00:30` попадает в строку за `2024-03-09`.

Лечится явным приведением: `generate_series(p_start_date::timestamp, p_end_date::timestamp, ...)`.
Тогда день - это чистая календарная арифметика, обе стороны сравнения имеют тип `timestamp`, и
часовой пояс сессии ни на что не влияет. На T-SQL такой проблемы нет: там `datetime2` не знает про
часовые пояса, а границы и так приводятся явно.

Случай закрыт тестами `A_range_crossing_a_midnight_dst_shift_still_returns_every_day` и
`A_payment_lands_on_its_own_calendar_day_whatever_the_session_time_zone`: на старой версии функции
они краснеют, на текущей проходят.

### Откуда берутся дни

Дни нужно породить, а не взять из таблицы платежей: в задании требуется строка и на те дни, когда
платежей не было.

**PostgreSQL** - `generate_series`, ограничений по длине интервала нет.

**SQL Server** - таблица-счётчик (tally) из перекрёстных соединений. Рекурсивный CTE здесь не
подходит: инлайн-табличная функция не может нести `OPTION (MAXRECURSION 0)`, поэтому рекурсия
остановилась бы на 100 днях, а задание прямо говорит про несколько лет.

Пять удвоений дают `2^32` строк - это больше, чем 3 652 059 дней, вообще представимых в типе
`date`, так что никакой интервал не может исчерпать счётчик. Четырёх уровней (65 536 дней, около
179 лет) было недостаточно: запрос на больший интервал возвращал **неполный результат без всякой
ошибки**, что хуже медленного ответа. `TOP` ограничивает то, что материализуется, поэтому
неиспользованные уровни ничего не стоят.

В SQL Server 2022 и новее вместо счётчика можно взять встроенную `GENERATE_SERIES`; счётчик выбран
потому, что работает на любой версии.

### `CASE` вокруг `TOP`

`TOP` не принимает отрицательное число, а `@Sd` может оказаться позже `@Ed`. В этом случае функция
возвращает пустой результат, а не ошибку.

### Покрывающий индекс

`amount` добавлен в `INCLUDE`, а не в ключ индекса: сортировать по нему незачем, а вот прочитать
сумму прямо из индекса - полезно, тогда обращение к самой таблице не требуется вовсе. В планах это
видно как `Index Only Scan` с `Heap Fetches: 0`.

### `STABLE`, `PARALLEL SAFE` и отсутствие `SET search_path`

`STABLE` - функция только читает, поэтому планировщик вправе вызвать её один раз на скан, а не на
каждую строку. `PARALLEL SAFE` разрешает параллельный план, что и нужно на интервале в несколько
лет.

`SET search_path` намеренно не задан, хотя обычно это часть защиты функции. Любая `SET`-секция
делает SQL-функцию непрозрачной для встраивания, а именно встроенное тело позволяет планировщику
добраться до индекса. Вместо этого все имена внутри указаны вместе со схемой. Тело с `WITH`
встраиванию не мешает: в плане видно, что параметры подставлены константами.

### Ноль вместо `NULL`

`LEFT JOIN` даёт `NULL` для дней без платежей; `COALESCE` (в PostgreSQL) и `ISNULL` (в SQL Server)
превращают его в `0`, как требует задание.

## Как запустить

PostgreSQL:

```bash
docker exec -i finbeat-taskmanagement-postgres-1 \
  psql -U postgres -d finbeat_taskmanagement < sql/postgresql/client_daily_payments.sql

docker exec finbeat-taskmanagement-postgres-1 \
  psql -U postgres -d finbeat_taskmanagement \
  -c "SELECT * FROM client.get_daily_payments(1, '2022-01-02', '2022-01-07');"
```

SQL Server:

```sql
SELECT * FROM client.GetDailyPayments(1, '2022-01-02', '2022-01-07');
```

## Проверка

Обе реализации выполнены на живых серверах - PostgreSQL 16.15 и SQL Server 2025 - и оба примера из
задания совпали построчно. Дополнительно проверено: интервал в пять лет возвращает 1827 дней, включая
оба високосных; интервал `1000-01-01..1999-12-31` возвращает 365 242 дня, ровно `DATEDIFF + 1`;
начало позже конца возвращает пустой результат; неизвестный клиент получает строку на каждый день с
нулями.

Новая и старая версии сверены построчно на тех же 2 млн платежей: по 60 клиентам за шесть лет
расхождений нет ни в PostgreSQL, ни в SQL Server. То есть переписывание изменило только план
выполнения, а в зонах с переводом часов в полночь ещё и исправило ответ.

Для PostgreSQL это закреплено автотестами `ClientDailyPaymentsTests`: они применяют скрипт ровно в
том виде, в каком он лежит в репозитории, загружают те самые шесть строк из задания и сверяют оба
результата. Для T-SQL автотестов нет - это потребовало бы образа SQL Server на 2,4 ГБ в каждом
прогоне, поэтому он проверен вручную.
