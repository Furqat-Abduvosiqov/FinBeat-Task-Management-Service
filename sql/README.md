# Задание 2 — поденные суммы платежей

Табличная функция принимает `ClientId` и интервал дат и возвращает по одной строке на каждый
календарный день интервала (обе границы включаются) с суммой платежей клиента за этот день. Если
платежей в этот день не было, в строке стоит `0`, а не пропуск. Интервал может охватывать несколько
лет.

## Файлы

| Файл | Назначение |
|---|---|
| `sqlserver/ClientDailyPayments.sql` | Буквальное прочтение задания: типы `bigint` / `datetime2(0)` / `money`, инлайн-табличная функция |
| `postgresql/client_daily_payments.sql` | Та же логика на PostgreSQL — эту версию проект умеет запускать, и она покрыта автотестами |

В задании таблица названа `ClientPayments` в DDL и `client.Payments` в примерах. Здесь используется
вариант со схемой: `client.Payments` в SQL Server и `client.payments` в PostgreSQL.

## Соответствие типов

| Задание (T-SQL) | PostgreSQL | Почему так |
|---|---|---|
| `bigint` | `bigint` | Совпадает |
| `datetime2(0)` | `timestamp(0)` | Момент без часового пояса, точность до секунды. Не `timestamptz`: иначе переход на летнее время сдвигал бы границы суток |
| `money` | `numeric(19, 4)` | `money` в SQL Server — это масштабированное целое с четырьмя знаками после запятой; `numeric(19, 4)` даёт ту же точность без потерь. Тип `money` в PostgreSQL зависит от локали, поэтому он не подходит |

## Принятые решения

### Соединение по полуоткрытому интервалу, а не приведение колонки к дате

Очевидная запись — `CAST(p.Dt AS date) = Days.Dt` (или `date(payments.dt) = days.dt`). Она
работает, но делает индекс по `(ClientId, Dt)` бесполезным: сервер обязан вычислить выражение для
каждой строки, а значит прочитать все платежи клиента за всю историю.

Поэтому день сравнивается с сырой колонкой как полуоткрытый интервал `[день, день + 1)`. Это
условие индекс отрабатывает как диапазонный поиск, и читаются только строки внутри интервала.

### Откуда берутся дни

Дни нужно породить, а не взять из таблицы платежей: в задании требуется строка и на те дни, когда
платежей не было.

**PostgreSQL** — `generate_series`, ограничений по длине интервала нет.

**SQL Server** — таблица-счётчик (tally) из перекрёстных соединений. Рекурсивный CTE здесь не
подходит: инлайн-табличная функция не может нести `OPTION (MAXRECURSION 0)`, поэтому рекурсия
остановилась бы на 100 днях, а задание прямо говорит про несколько лет.

Пять удвоений дают `2^32` строк — это больше, чем 3 652 059 дней, вообще представимых в типе
`date`, так что никакой интервал не может исчерпать счётчик. Четырёх уровней (65 536 дней, около
179 лет) было недостаточно: запрос на больший интервал возвращал **неполный результат без всякой
ошибки**, что хуже медленного ответа. `TOP` ограничивает то, что материализуется, поэтому
неиспользованные уровни ничего не стоят.

В SQL Server 2022 и новее вместо счётчика можно взять встроенную `GENERATE_SERIES`; счётчик выбран
потому, что работает на любой версии.

### `CASE` вокруг `TOP`

`TOP` не принимает отрицательное число, а `@Sd` может оказаться позже `@Ed`. В этом случае функция
возвращает пустой результат, а не ошибку.

### Покрывающий индекс

`amount` добавлен в `INCLUDE`, а не в ключ индекса: сортировать по нему незачем, а вот прочитать
сумму прямо из индекса — полезно, тогда обращение к самой таблице не требуется вовсе.

### `STABLE`, `PARALLEL SAFE` и отсутствие `SET search_path`

`STABLE` — функция только читает, поэтому планировщик вправе вызвать её один раз на скан, а не на
каждую строку. `PARALLEL SAFE` разрешает параллельный план, что и нужно на интервале в несколько
лет.

`SET search_path` намеренно не задан, хотя обычно это часть защиты функции. Любая `SET`-секция
делает SQL-функцию непрозрачной для встраивания, а именно встроенное тело позволяет планировщику
добраться до индекса. Вместо этого все имена внутри указаны вместе со схемой.

### Ноль вместо `NULL`

`LEFT JOIN` даёт `NULL` для дней без платежей; `COALESCE` (в PostgreSQL) и `ISNULL` (в SQL Server)
превращают его в `0`, как требует задание.

## Как запустить

PostgreSQL:

```bash
docker exec -i finbeat-taskmanagement-postgres-1 \
  psql -U postgres -d finbeat_taskmanagement < sql/postgresql/client_daily_payments.sql

docker exec finbeat-taskmanagement-postgres-1 \
  psql -U postgres -d finbeat_taskmanagement \
  -c "SELECT * FROM client.get_daily_payments(1, '2022-01-02', '2022-01-07');"
```

SQL Server:

```sql
SELECT * FROM client.GetDailyPayments(1, '2022-01-02', '2022-01-07');
```

## Проверка

Обе реализации выполнены на живых серверах — PostgreSQL 16 и SQL Server 2025 — и оба примера из
задания совпали построчно. Дополнительно проверено: интервал в пять лет возвращает 1827 дней, включая
оба високосных; интервал в тысячу лет возвращает 365 242 дня, ровно `DATEDIFF + 1`; начало позже
конца возвращает пустой результат; неизвестный клиент получает строку на каждый день с нулями.

Для PostgreSQL это закреплено автотестами `ClientDailyPaymentsTests`: они применяют скрипт ровно в
том виде, в каком он лежит в репозитории, загружают те самые шесть строк из задания и сверяют оба
результата. Для T-SQL автотестов нет — это потребовало бы образа SQL Server на 1,5 ГБ в каждом
прогоне, поэтому он проверен вручную.
